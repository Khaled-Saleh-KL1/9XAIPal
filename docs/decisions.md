# Decisions & scar tissue

> **What this is:** approaches tried and abandoned, non-goals decided on purpose, and ugly things
> kept deliberately. One line each, newest last. Append; never rewrite an existing entry.
>
> **Why it exists:** none of this is recoverable from the code at any price. A rejected approach
> leaves no trace, so without a record it gets re-proposed every few months.
>
> **Format:** `DATE  Tried/Chose/Kept: <what>.  Because: <why>.`

2026-07-28  Chose: whole-collection `PUT /papers/{id}/decks` instead of per-deck CRUD.  Because: one drag can dissolve a deck, create another, and move a card between two more: granular calls turn that into an ordered sequence with a half-applied state between each, and a dropped request leaves a card in two decks or none.

2026-07-28  Chose: two nullable FKs (`ai_note_id`, `personal_note_id`) + a `CHECK`, over one polymorphic member id.  Because: it buys real cascade behaviour: deleting a note removes it from its deck, instead of leaving a dangling reference the client has to notice and skip.

2026-07-28  Tried: HTML5 drag-and-drop for stacking margin cards.  Failed: no touch support at all, and the app is meant to be opened from a tablet over the LAN. Replaced with pointer events, which cost a hand-rolled hit test via `elementFromPoint`.

2026-07-28  Tried: gating the localStorage→server migration on "server has none of this collection".  Failed: StrictMode's double mount ran it twice and imported every note in duplicate. Replaced with a shared in-flight promise plus `(anchor, body)` matching, which also makes a half-finished migration resumable.

2026-07-28  Kept ugly on purpose: the API image installs the full `requirements.txt`, MinerU and torch included, though only the Celery worker extracts PDFs.  Because: one requirements file is the repo's single source of truth, and splitting it into api/worker sets is a second thing to keep in sync. Known cost: a multi-GB API image. Do not grow it; split the requirements if it starts hurting.

2026-07-28  Chose: `requirements.txt` in both Dockerfiles, not `pyproject.toml` + `uv.lock`.  Because: both are gitignored at the repo root, so they can never exist in a clone, and every `docker compose build` died at the `COPY`. uv still does the install, so the speed was never the point.

2026-08-18  Chose: give the paper agent the anchored passage plus the paper's contents index, never the paper.  Because: a note is a question about one passage, and a paper that merely fits in the window is not a reason to spend the window on it: the model drifts into summarising the document instead of reading the sentence. `PAPER_WHOLE_DOCUMENT_CONTEXT` keeps the old behaviour reachable, off by default. What makes it safe is the index, not the tools: a model that can see the document's shape can name the section it wants, where one with neither has only guesses at the paper's vocabulary.

2026-08-18  Kept ugly on purpose: the default note path answers from a NON-streamed probe call, so the answer lands whole instead of typing itself out.  Because: with a text tool protocol any reply may turn out to be a `<tool>` block, and streaming one into the margin would put "SEARCH: …" on screen. Detecting it mid-stream was considered and rejected: a model that writes a sentence of preamble before its tool block would have already leaked that sentence, and recovering means either resetting a card the reader is watching or discarding a real answer. Generation time is unchanged; only the reveal is, and `lib/pacer.ts` still paces it. Do not "fix" this without solving the preamble case.

2026-08-18  Chose: promote a drag-selection inside a table to a whole-table anchor, rather than quoting the cells that were crossed.  Because: dragging a table yields "8.4 12.1 91.2 7B", values stripped of the header saying which metric and the row label saying which model. That quote is not merely worse, it is unanswerable in a way that looks answerable, and the model would confidently answer about numbers it cannot attribute. A table is one unit, like a figure: the MinerU crop goes to the model and the transcription rides along as fallible.

2026-08-26  Chose: Tavily as the default web-search provider, keeping SearXNG behind `WEB_SEARCH_PROVIDER=searxng`.  Because: SearXNG returns SERP rows that still need scraping to be useful to a model, and the [Exa + Firecrawl plan](archive/2026-08-26/exa-firecrawl-research-stack.md) that was meant to fix that is two vendors and a scraping pipeline for the same outcome. Tavily returns ranked, already-extracted page text in one call. The real cost is not quality but privacy: SearXNG ran on localhost so a query never left the machine, and a Tavily query does. That is why the old provider stays one env line away rather than being deleted, and why the hole is now stated twice in [overview.md §7](02-architecture/overview.md#7-what-never-happens).

2026-08-26  Chose: report every agent tool call to the reader, live as `step` events, and persisted in `paper_notes.agent_steps`, rather than only logging them.  Because: the agent can spend six rounds fetching before it writes a word, and from the reader's side that is a spinner followed by a confident paragraph, which is indistinguishable from a model that made it up. The trail turns an assertion into something checkable: these sections, that search, this source. Persisting it is what makes the verbosity worth anything: a note reopened next week is otherwise back to being unattributable.

2026-08-26  Chose: `THINK:` as a no-op line inside the tool block, rather than asking the model to explain itself in prose.  Because: prose outside the block cannot be shown next to the fetch it explains and would leak into the answer on the round the model stops calling tools. A line inside the block costs no round, executes nothing, and lands exactly where the reader needs it. It rides on the first call of a round only: repeated across three fetches it reads as three separate reasons.

2026-08-26  Chose: one "Panel" button in the reader's bottom-left corner, replacing the "Ask" and "Note" pair.  Because: both anchored to whatever block happened to be at the top of the viewport, a worse version of what highlighting already does, offered more prominently. Two levels now have two surfaces: highlight for the passage, the panel for the paper. The corner means exactly one thing, and the cross-paper level has somewhere to land.

2026-08-26  Chose: a `scope` column on `paper_notes` rather than inferring the surface from `anchor_kind` at render time.  Because: the client would have to re-derive it in the gutter layout, the panel list, and the margin-balancer, and the three would drift. `scope` is still derived server-side from `anchor.kind` and never accepted as a request field: a row saying `kind='document', scope='anchor'` has no coherent meaning and no surface could place it.

2026-08-26  Chose: render library covers lazily on first request, cached to `storage/covers/`, instead of at ingestion.  Because: ingestion is already the slow path the reader waits on, a cover is worth nothing until the library is looked at, and doing it lazily gives covers to every paper ingested before the feature existed for free. The endpoint answers 204 rather than 404 when a page will not rasterise: the grid asks for one cover per card, and a wall of 404s makes a working library look broken.

2026-08-26  Chose: rename a paper by setting `documents.title`, never by touching `filename` or `original_filename`.  Because: `filename` is the on-disk key every storage path is built from and `original_filename` is what `/raw` serves the download as, so renaming either to match a label breaks both. The cost is that the Raw files panel still lists arXiv ids, which is correct: that panel is about files.

2026-08-26  Chose: make the holistic level a page (`#/desk`) and delete the in-reader panel, rather than growing the panel into a tab strip.  Because: a question about several papers is not something you do *on top of* a document you are reading: an overlay says the thing underneath is the subject, and on the desk it is not. The reader's corner button became a door instead of a drawer. Cost: the `scope='document'` notes made during the panel's one iteration have no surface that creates new ones, so they are folded into the reader's Marginalia index to stay findable rather than being migrated or dropped.

2026-08-26  Chose: a `studies` table with explicit `position`, written whole-collection, over a folder-ish membership with add/remove calls.  Because: answers cite papers as P1/P2/P3 and that numbering comes from `position`, so a partial update, or a re-order that looks cosmetic, silently repoints every citation the reader has already read. Same reasoning as note decks: send the list you want, and the list order IS the ordering.

2026-08-26  Chose: `study_id IS NULL` means the library-wide chat, rather than a sentinel row or a separate table.  Because: "every paper" is a real scope the reader switches to constantly, not an unassigned state, and giving it a row would mean seeding it on first run and keeping it undeletable. The cost is that every query needs `IS NOT DISTINCT FROM` instead of `=`, which is written down in the repository because `study_id = NULL` silently matches nothing.

2026-08-26  Chose: give the study agent only the heading spines of its papers, never their text.  Because: ten papers is easily a million tokens and there is no context window that makes stuffing them an option. This is the paper agent's bet taken where there is no alternative, and it works for the same reason: a model that can see the shape of every document can name the section it wants.

2026-08-26  Kept ugly on purpose: `sticky_notes` is a second note table alongside `personal_notes`.  Because: a personal note is anchored to a block and lives in one document's margin; a sticky has no anchor, may name several papers or none, and lives on the desk. Merging them would give every sticky an `anchor_sequence_id` that means nothing and would surface stickies in the margin layout. Two small tables beat one table with a column that is meaningless for half its rows.

2026-08-26  Tried: rendering a study answer by splitting it on its `[[P2:41]]` markers and rendering each fragment as markdown.  Failed: every fragment becomes its own block, so a citation mid-sentence breaks the paragraph in two and strands the rest, including a lone trailing full stop, on its own line. Replaced with a text transform to links plus a `components.a` override, which keeps the paragraph intact.

2026-08-26  Chose: filter the forced final turn's token stream for a leaked `<tool>` block instead of stripping it afterwards.  Because: it is not hypothetical. The first live desk question ended with "tool> THINK: verify P3's cost claim… SECTION: P3:29" in the middle of the answer. By the time a strip could run the tokens are on screen, and only a refetch quietly replaces them. The filter holds back the last few characters per token because the marker splits across boundaries ("<to" + "ol>"). Both agents route through it; the paper agent had the same latent hole.

2026-08-26  Chose: scope chat notes by conversation (`board='chat'` + `study_id`) and give universal notes their own page, rather than scoping notes by paper.  Because: a note is a thought about a line of enquiry, and a line of enquiry is a conversation: "compare these three on decode cost" belongs to the chat that produced it, not to any one of the three papers. Paper references survive as a tag (`sticky_note_papers`) because they are useful metadata on the wall, but they no longer decide which board a note appears on.

2026-08-26  Chose: a `board` column alongside the nullable `study_id`, even though it looks redundant.  Because: `study_id IS NULL` already means the library-wide CHAT, a real scope, not an absence, so without `board` a note beside that chat and a note on the universal board are literally the same row. The apparent redundancy is what keeps two different things distinguishable.

2026-08-26  Chose: enforce "only the reader deletes a note" structurally rather than with a permission flag.  Because: a flag is a check that can be forgotten at a new call site. Instead there is no delete tool in the agent's parser, `study_agent` does not import `delete_sticky`, and `POST /stickies` hard-codes `origin='user'` so no client can forge an assistant note either. The rule is also stated in the prompt at the point of temptation, but the prompt is the courtesy, not the enforcement.

2026-08-26  Chose: `origin` is not patchable.  Because: the badge records where a claim came from, not who typed last. If editing an assistant note turned it into the reader's own, the badge would be worthless exactly when it matters: a week later, deciding whether you concluded something or a model asserted it.

2026-08-26  Tried: giving the agent only the `NOTE:` tool-block syntax.  Failed: asked to "pin a note", it wrote `<note>…</note>` into its answer on the first attempt. The forced final turn is told it has no tools, so a NOTE: line genuinely is not available there, and it improvised a tag. Now supported deliberately: parsing it is meeting the model where it is; refusing to would leave raw XML in the reader's answer and nothing on the board. Both syntaxes work, and the tag is stripped from what the reader sees.

2026-08-26  Tried: extracting `<note>` blocks only in `stream_answer`.  Failed: the model can answer on the very first probe without calling a tool, and that path never streams, so the raw tag stayed in the answer precisely when the reader had asked for a note. `_pin_written_notes` is now called from both exits of the loop.

2026-08-26  Chose: short-circuit a repeated tool call with "you already fetched this" instead of re-running it.  Because: observed, the model re-requested the same three SECTIONs on four consecutive rounds: twelve identical fetches and half the round budget spent making no progress. It can see the results in WHAT YOU HAVE GATHERED, but a fresh copy reads to it as confirmation rather than repetition. Saying so costs nothing and is the signal that moves it on.

2026-08-26  Fixed: three studies all named "Whole library".  Cause: `StudyNameInput` seeds its draft from `initial` on mount only, and "create then rename" set `renaming` before the new study had loaded, so the box opened holding the PREVIOUS study's name and committed it on blur. Now keyed on the study id AND deferred until the new study is in state. Worth recording because the symptom (duplicate names) looks like a backend or a user problem and is neither.

2026-08-26  Chose: derive the wall's note tilt from the note id, never `Math.random()`.  Because: a random rotation re-rolls on every render, so every keystroke in the filter box would make the whole wall twitch. Same id, same angle, forever.

2026-08-26  Tried: CSS multi-column (`columns: 260px`) for the notes wall's masonry.  Failed in WebKit: multi-column fragments its children, so a note taller than the remaining column height was split and its bottom re-drawn at the top of the next column, pin, dashed border and all, which read as two broken half-notes stranded under the board. `display: inline-block; width: 100%`, the usual charm against fragmentation, was not enough there. Replaced with a CSS grid, whose items never fragment in any engine. The masonry is the price: rows are ragged rather than packed, which for a corkboard is not a loss. Do not restore the columns without testing WebKit.

2026-08-26  Tried: deciding the notes wall's "there is more below" fade in CSS, with `:has(> :nth-child(3))`.  Failed: it counts block children, and a long note is usually ONE long paragraph, so the exact notes that needed the fade did not get it, and clamped with a hard cut through the middle of a line. CSS cannot ask "did this overflow", so StickyNote measures scrollHeight against clientHeight and sets a class, with a ResizeObserver because a note that fits at first paint can overflow once the serif face swaps in.

2026-08-26  Chose: derive heading depth from the paper's own section numbering rather than from `chunks.heading_path`.  Because: MinerU's `text_level` only separates the document title from everything else, so `heading_path` is depth 2 for both "3 Training data" and "3.1 ARC task formulation": the contents panel and both agents' indexes rendered as flat columns with no hierarchy at all. "3.1" is a more reliable statement of depth than any layout heuristic, it is already in the text, and it fixes every paper already ingested without a re-chunk. `heading_path` remains the fallback for papers that number nothing. Fixing it in the chunker instead would have been the "right" layer and would have required re-ingesting the whole library to see any benefit.

2026-08-26  Tried: styling contents nesting as a class per level, `.outline-l1` … `.outline-l4`, with `Math.min(level, 4)`.  Failed on the next paper: Kimi K3 numbers to "2.1.1", and a fourth level existed but a fifth silently flattened: the clamp made "2.1.1.1" render level with its own parent, which is the exact bug the nesting was meant to fix, one level down. Replaced with a `--depth` custom property and one calc(); the indent step and the rail offset are now the only two numbers, instead of four hand-written pairs that could drift.

2026-08-26  Learned: `docker compose up -d --no-deps api` on its own is not a safe deploy.  Because: it was how the skew above happened. The api container was rebuilt repeatedly while celery_worker kept running months-old code, and the two only have to agree on task names for that to be invisible until an ingestion silently vanishes. Recreate `api` and `celery_worker` together, always.

2026-08-26  Fixed: a NUL byte in MinerU's output killing an entire ingestion at the insert.  Because: Postgres `text` cannot store 0x00, so one bad character in one block failed the whole batch after all the extraction work was done, and surfaced as a generic "restart the backend and try again". Scrubbed at the funnel both chunk builders return through, so the pipeline and /rechunk are covered once rather than twice.

2026-08-26  Learned: the Celery app name is a wire identifier, not a label.  Because: renaming it (tried on a fork) changes every task name: the API began dispatching `<newname>.process_ingestion` while the worker still registered `9xaipal.process_ingestion`, so Celery received the message, failed to match it, and DISCARDED it. A live ingestion sat at "queued · 0%" forever, and nothing in the UI could tell that the task no longer existed. If the project is ever renamed, POSTGRES_DB, the role, container names, volume names and the Celery app have to move in one step.

2026-08-29  Reversed the 2026-07-28 `requirements.txt` decision above: moved to `pyproject.toml` + `uv.lock`, un-gitignored.  Because: a flat requirements file makes `uv pip install -r` re-resolve and re-check every package on any single-line change, so one new dependency invalidated the whole install layer. `uv sync --locked` diffs against the committed lockfile instead, so an unchanged lock resyncs in ~1-2s and adding one dependency only fetches that one. This also fixed the api/worker split without reintroducing a second file to hand-sync: the mineru extra (`uv sync --extra mineru`) IS the split, so the 07-28 "one file, single source of truth" entry above still holds, just expressed as one manifest with an optional extra instead of one flat file both images installed in full. Torch/torchvision are listed directly in `pyproject.toml`'s `mineru` extra (not left to resolve purely transitively through mineru) because `tool.uv.sources`' CPU-only index override does not apply to a package that's only transitive — verified the hard way: without this, torch silently re-resolved from PyPI's default CUDA build the moment `mineru` was added to the graph.

2026-08-31  Removed SearXNG entirely; replaced the single-active-provider model with a 6-provider cascade (google, tavily, linkup, exa, serpapi, duckduckgo).  Because: asked to verify the "SearXNG fallback" was actually trustworthy, found it wasn't — two independent problems, neither hypothetical. First, production had no SearXNG container at all (never in `docker-compose.prod.yml`) and `WEB_SEARCH_PROVIDER` was hard-pinned to `tavily`, so the documented auto-fallback never engaged even if Tavily went down. Second, even once a real SearXNG instance was stood up to test, `external_context.py`'s `categories=["it","science"]` filter made it return garbage: SearXNG's `score` field is a per-engine position weight, not a comparable relevance score, so restricting to several engines at once let Docker Hub and GitHub's own "#1 picks" tie with and beat the actual paper for a query as plain as "FlashAttention 2 paper" — verified live, both broken (top-5 all irrelevant) and fixed (same instance, no category filter, correct paper first). Tavily never hit this because its client silently ignores `categories` — pure luck that the bug never shipped visibly. Replaced the whole "pick one provider" model with a real cascade: `search()`/`search_images()` try each configured provider in order and fall through to the next on any exception OR an empty result, verified end-to-end with deliberately broken keys forcing every single hop including the full depth to `duckduckgo` (which needs no key and is always eligible, so `WEB_SEARCH_PROVIDER=none` is now the only way to fully disable web search). `google_api_key` is a real, auth-valid Gemini Search-grounding key but has hit `429 RESOURCE_EXHAUSTED` on every live grounding call so far — plausibly the EEA free-tier grounding restriction, unconfirmed since it can't be checked from outside Google's own console — left first in the cascade anyway since the code is correct and the cascade absorbs the failure by design.

2026-09-01  Gave chat the same provider cascade as web search: `resolver.llm_cascade()` + retry loops in `client.chat()`/`stream_chat()`/`chat_sync()`.  Because: the old resolver picked ONE target per call (Ollama if its cheap `/api/tags` probe passed, else the first cloud key) and stopped — if Ollama passed the probe but the real completion call then failed (wrong model, OOM, mid-generation crash), the whole request died even with a cloud key sitting in `.env`. Now every failure past the probe falls through to the next configured provider with the SAME messages, same shape as the web search cascade. Streaming gets one deliberate asymmetry: fallback only covers failures BEFORE the first token reaches the caller — once a token has already been shown in the UI, a later failure raises instead of silently discarding visible output and restarting on a different provider/model/voice mid-answer. `chat()`/`chat_sync()` have no such limit (no partial output is ever visible), so any failure at any point falls through cleanly. Verified with 19 new unit tests (mocked failures at every cascade position, streaming's pre/post-first-token split, real-messages-object identity across retries) plus a live forced-failure check against production's real Ollama Cloud endpoint. Could not verify a real successful cross-provider handoff end-to-end: production has exactly one working LLM credential (Ollama Cloud) at the time of this change, so there is no second real backend to hand off to yet — same category of gap as the `google_api_key` entry above, closed by code correctness + mocked coverage rather than a live success, until a second key is added.

2026-09-01  Added a circuit breaker to both provider cascades, and a hard Redis-counted daily cap on Google search.  Because: auditing the cascades found the first provider in the web search chain was permanently dead — a free-tier Gemini grounding key, and free-tier Gemini is unavailable in the EEA, so every call from this France-hosted box returned 429. The cascade handled it correctly (fell through to Tavily every time) but re-paid for it forever: ~0.13s of every single search, a third of total search latency, plus an ERROR log line per search, with no possible code-side fix. Rather than drop Google from the order the user explicitly wanted it first in, providers now trip out after 3 consecutive failures and are skipped for 5 minutes, keeping their priority so a recovered provider is picked up automatically with no config change. `filter_open` deliberately returns the FULL list when everything is tripped — a slow answer beats no answer. Making that work required a real contract change: every search client used to swallow its own errors and return `[]`, which made "I broke" and "I found nothing" indistinguishable (and made web.py's `except Exception` branch dead code — nothing could ever raise). Clients now raise `ProviderError` for genuine failures and reserve `[]` for genuinely-empty results, so the breaker trips on the former and never on the latter. Separately, the user supplied a working Custom Search key (the earlier one was the wrong product entirely) with an explicit "must never exceed 100/day so I don't pay": that cap is enforced in code before every call, counted in Redis so it holds across both API workers AND the Celery worker (three in-memory counters would each allow a full 100), reserved before the request and never refunded on failure (miscounting can only ever keep us under), keyed to US/Pacific days to match Google's own reset rather than UTC, and failing CLOSED if Redis is unreachable — an uncountable call is exactly the one that could bill. Also un-pinned `LLM_PROVIDER: ollama` in prod compose back to `auto`: a pin means one backend with no fallback, which would have silently defeated the chat cascade the moment a second LLM key was added.

2026-09-01  Dropped Google from web search entirely; added per-key rotation for Tavily and Ollama.  Because: Google was tried twice and neither surface was worth a cascade slot. Gemini Search grounding was geo-blocked (free tier unavailable in the EEA, 100% 429 from this France-hosted box); the Custom Search JSON API worked but gives only 100 free queries/day before it bills, and the deliberate rule for this deployment is that no provider should be *able* to cost money. Both are gone, along with app/search/quota.py which existed solely to cap Google's daily spend. Replaced with something that scales for free instead: TAVILY_API_KEY and OLLAMA_API_KEY now accept COMMA-SEPARATED LISTS, since both vendors meter per key. Tavily rotates inside its own client (401/403/429 → next key; a 5xx or network error fails the provider immediately, because every key would hit the same wall and burning one request per key to prove it is waste). Ollama instead expands into one LLMTarget per key, so the existing chat cascade handles rotation with no new machinery — which also required giving LLMTarget a per-key `breaker_id` (`ollama#0`, `ollama#1`), or one spent key would have tripped the circuit breaker for every key at once. ⚠ Threading the key through exposed a bug that only a live test could catch: ollama_client read `settings.ollama_api_key` directly rather than taking the key from its target, so with a list configured it sent the whole comma-joined string as one Bearer token and 401'd on EVERY key — including the valid one — while the cascade "correctly" fell through all of them to failure. Fixed by passing `target.api_key` explicitly through chat/stream_chat/chat_sync, with a regression test asserting each attempt carries exactly one key and never the join. Verified live end to end: Tavily key1→key2→key3 rotation, then tavily→linkup→exa→serpapi→duckduckgo for both text AND images, and ollama#0→ollama#1→ollama#2 for both streaming and non-streaming chat.
